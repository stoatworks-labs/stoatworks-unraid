# Notes

Working notes for this repo: status, decisions, and the traps that have actually bitten.
Migrated out of Claude Code's memory on 2026-08-24, so they are written in the first
person and dated by when each thing was learned — that date is usually the useful part.

Cross-cutting notes that are not specific to this repo live in
[fleet-notes](https://github.com/stoatworks-labs/fleet-notes).

*stoatworks-unraid — generator repo producing Docker + Unraid CA packaging for the whole web fleet from two JSON files*

`~/Projects/stoatworks-unraid` (created 2026-08-04, **public, on `main`**) is the
single source for containerising the web fleet. `fleet.json` + `unraid.json`
drive `scripts/gen-docker.mjs` and `scripts/gen-templates.mjs`, which write ~153
files into 27 app repos plus 27 CA templates. **Never hand-edit the generated
Dockerfile / compose / nginx.conf / workflow in an app repo** — regenerate.

Three fleet facts that cost time to establish and aren't obvious from any repo:

- **`atem-scopes` builds its web app with `static:build`, not `build`** — plain
  `build` is `electron-vite build` and yields the desktop app.
- **`caspar-av/web/` is untracked**, built from `console/` by Vite. A Rust-only
  image serves nothing.
- **`flock` already had a hand-written Dockerfile + compose**, better informed
  than generated output (Debian ffmpeg may not link libsrt). Left alone via
  `hasOwnDocker`.
- **`pmse-to-wwb` is a FastAPI service, NOT a static site.** Its `wrangler.toml`
  serves `site/`, but that Cloudflare page is only a signpost — the converter
  parses the PDF server-side. Classifying it from the wrangler config alone
  produced an image that shipped the signpost and no app. Also `hasOwnDocker`.

**CA is pointed at THIS repo, never at an app repo.** Community Applications
reads templates only from the templates repository; the app repos hold
Dockerfiles and CA never looks at them. Submitting an app repo fails with "No
ca_profile.xml found." That file is required at the templates repo **root**:
root element `<CommunityApplications>`, with `<Profile>` as prose describing the
repository (not a container of fields), plus `<Icon>`, `<WebPage>`, `<Forum>`.
Generated by `gen-templates.mjs` from `unraid.json`'s `profile` block.

**The website repo is PRIVATE, so its raw URLs 404 anonymously** — CA, and
anything else unauthenticated, cannot fetch the brand mark from
`stoatworks-labs.github.io` however correct the path. `gh api` still works and
returns a tokenised `download_url`, which makes the file look reachable when it
is not. The mark is therefore committed to `stoatworks-unraid/icon.png` and
served from there. See [website repo name](https://github.com/stoatworks-labs/fleet-notes/blob/main/notes/reference_website_repo_name.md).

**GHCR packages only go public if the package is linked to its repo.** GitHub
infers the link when the image name matches the repo name; where it does not —
`stoatworks-website` is built from `stoatworks-labs.github.io` — the package
stays PRIVATE and an anonymous pull 403s while the other 27 work. The workflows
now set `org.opencontainers.image.source`; the website package still needs its
visibility flipped once by hand. Verify with an anonymous
`ghcr.io/token?scope=repository:stoatworks-labs/<img>:pull` + manifest HEAD —
a green Actions run does NOT prove the image is pullable.

**Host ports are hand-allocated and must stay distinct** — a server running the
whole fleet gets 28 containers. On `network_mode: host` (flock, srt-router,
atem-overseer, RFutils) Unraid's port field does nothing: the process binds the
host directly, so two host-networked containers sharing a default means the
second dies with EADDRINUSE. flock keeps 8080; srt-router moved to 8091 (its
port lives in the seeded TOML, so the entrypoint rewrites it at seed time only,
overridable with `WEB_PORT`); caspar-av's bridge default moved to 8092. Re-run
the collision check over `templates/*.xml` after adding any app.

Serving directories are committed and prebuilt for 12 repos (`demo/`, `site/`,
`web/public/`) — no build stage. The 3 wasm demos ship self-contained JS, no
`.wasm` files, so no emscripten needed.

`_headers` is the source of truth for headers; nginx can't read it, so it's
translated. See [nginx add header inheritance](https://github.com/stoatworks-labs/fleet-notes/blob/main/notes/reference_nginx_add_header_inheritance.md).

Related: [observability sweep](https://github.com/stoatworks-labs/fleet-notes/blob/main/notes/project_observability_sweep.md), [website repo name](https://github.com/stoatworks-labs/fleet-notes/blob/main/notes/reference_website_repo_name.md).

## 2026-08-05 (later) — PUBLIC, and the whole fleet's images are green

`stoatworks-unraid` is now **github.com/stoatworks-labs/stoatworks-unraid, PUBLIC, MIT**.
**Its default branch must be `main`**: `gen-templates.mjs` hard-codes
`raw.githubusercontent.com/stoatworks-labs/stoatworks-unraid/main` and `iconBase` builds
`/main/` URLs, so a repo left on `master` 404s every template and icon in Community
Applications. `gh repo create --source=.` pushes whatever the local branch is called —
rename before or straight after.

The generated packaging is now **committed and pushed in all 26 repos with a remote**, and
**every image builds green on main**. Two real defects surfaced the moment CI ran, and
both are the same lesson:

> **A container build is the first clean-room install a repo has ever had.** Everything
> else on this machine installs on top of an existing `node_modules` or an incremental
> Cargo cache, so a broken lockfile or an unread dependency bump can sit there for weeks
> looking fine.

- **caspar-av's console could not `npm ci` at all.** Dependabot PR #10 was a *major*
  bump of `react-dom` 18 → 19 that landed without `react` being bumped with it; react-dom
  19 has react 19 as a peer, so ERESOLVE. Reverted to the 18 line rather than upgraded —
  the console is React 18 code and the bump was merged unread. The Rust stage then failed
  on axum 0.8's `Message::Text(Utf8Bytes)`; a co-session fixed that in parallel.
- **pmse-to-wwb's generated image served the wrong thing entirely.** Its `site/` is a
  four-file *landing page* pointing at RFutils, not the app, so a `static-prebuilt` entry
  turned a self-hostable converter into a self-hosted redirect notice. It is now
  `hasOwnDocker` (like flock) with a new `python-service` kind that exists purely so the
  template reads port 8000 instead of the 80 a static kind forces. **`serveDir` deserves a
  look at the directory, not just its name.**

`templates-private/` is empty.

## 2026-08-06 — narrowed to what you would actually run on a server

**fleet.json is 28 apps -> 15, and this is the scope rule now:** the ten browser
tools and the five always-on services (atem-overseer, RFutils, caspar-av,
srt-router, flock). **Out: the ten plugin browser demos, the srt-router
click-through demo (it rode along as an `extraImage`, easy to miss), and the
three websites.** A demo shows what an effect looks like; nobody installs that
on Unraid. The sites are already deployed. **16 templates, 74 generated files.**

The removals were done in the app repos too — `git rm` of Dockerfile,
.dockerignore, docker-compose.yml, docker/ and the workflow in all 11 dropped
repos with a remote, plus plain deletion in stoatworks-hire/productions, which
have no git. The reason to bother: **`gen-docker.mjs` only ever writes, it never
deletes.** Drop an app from fleet.json and its generated files stay behind in
that repo, still saying "edit fleet.json and regenerate" while regeneration no
longer touches them. Same trap for a removed `extraImage` or `variant`.

**Deleting a GHCR package needs `delete:packages` + `read:packages`, which the
gh token here does not have** (`gist, read:org, repo, workflow`). `gh auth
refresh -h github.com -s delete:packages,read:packages` is an interactive
sign-in, so the 11 orphaned demo packages had to be left for Allan. Probe
whether a package exists without any scope at all: get an anon token from
`ghcr.io/token?scope=repository:<owner>/<img>:pull` and GET the manifest — 200
means public, **403 means it exists but is private**, 404 means gone.

## 2026-08-06 (later) — submitted to CA; the wait is the feed build, not moderation

Submitted at `ca.unraid.net/submit`. The portal returned **`auto_approved`** and still showed
**0 apps** — that is not a failure. **Every counter on that page is derived from the published
feed, not from a live scan of the repo.** The gate is the feed rebuild in `Squidly271/AppFeed`,
which is irregular (five builds on 2026-08-05, one on 2026-08-06, none for two days before
that), so an approved repo reads as zero until the next one runs.

How to tell "not ingested yet" from "rejected", with no login:

- `raw.githubusercontent.com/Squidly271/AppFeed/master/applicationFeed.json` (23 MB) — grep the
  owner. Also `repositoryList.json` (the ~800 scraped repos, a **derived** artifact) and
  `log.txt` (the scrape log). Absent from all three **and** no log entry = never fetched.
- `assets.ca.unraid.net/feed/applicationFeed.json` carries `last_updated`. Compare it to the
  approval time before concluding anything is wrong.

**The official ground truth is `github.com/unraid/unraid-community-apps-starter`** — read that
before believing any forum post. It confirms the layout already in use (`ca_profile.xml` at
root, root element `<CommunityApplications>` with prose `<Profile>`; `<Maintainer>` also works
and is what IBRACORP uses; the file is optional) plus `templates/*.xml`, and that either
`<Support>` or `<Project>` is required, not both.

**Category tokens take no trailing colon on a subcategory.** `Tools:Utilities:` and
`MediaApp:Music:` are not tokens and are dropped, listing the app uncategorised — seven
templates had this. The colon belongs only on a bare top-level token (`Tools:`, `Other:`).
`MediaApp:Video Tools:` is fine: a space-separated list of two valid tokens. Validate against
`AppFeed/categoryList.json`, where the children are written `MediaApp-Video` and the templates
write `MediaApp:Video`. `<Registry>` is the **per-image** URL (`https://ghcr.io/<owner>/<img>`),
not the org packages page. Both fixed and pushed in `cf96497..323c8bb`.

GHCR is thoroughly supported — 1127 of the 4042 listed apps use it — so a GHCR image is never
the reason a listing is missing.

That probe caught a live bug on the way out: the `stoatworks-website` package
was **private**, because it is built from `stoatworks-labs.github.io`, which is
a private repo — while `unraid.json` recorded it as public and its template sat
in `templates/`. That is exactly the public-template-pointing-at-a-private-package
failure the file's own comment warns about, and it had been sitting there
unnoticed. Removing the entry took the bug with it.

## 2026-08-20 — both generators had been DEAD since the tree reorg

`gen-docker.mjs` and `gen-templates.mjs` resolved `join($HOME/Projects, repo)`,
which stopped existing when the tree split into `~/projects`, `~/hardware` and
`~/reverse-engineering`, each subdivided by discipline
([repo tree layout](https://github.com/stoatworks-labs/fleet-notes/blob/main/notes/reference_repo_tree_layout.md)). **Every repo resolved to nothing.** The
failure is quiet in the worst way: `gen-docker.mjs --dry-run` prints
**"Wrote 0 files."** and lists all 17 repos under "Notes (17)", which reads as
*nothing needed doing* rather than *I could not find any of your code*.

Fixed with **`scripts/repo-path.mjs`** — `resolveRepo(name, override)` scans the
three roots two levels deep (root itself, then each category), deliberately not
recursively so it cannot return a `node_modules` or build-tree directory that
merely shares a name. `--projects` / `PROJECTS_DIR` still force the old flat
layout. `gen-templates.mjs` needed it in two more places: the icon-on-disk check
and the `hasOwnTemplate` verbatim-copy lookup.

**Proving a generator fix is safe:** regenerate a repo whose output is already
committed — `node scripts/gen-docker.mjs --only blend-calc` — and check
`git status` in it. Clean means byte-identical, so the change is a pure fix.
Do that BEFORE a full run, because a full run writes into all 17 app repos.

☠️ **The store had been shipping a stale `templates/unfuckarr.xml` the whole
time.** unfuckarr sets `hasOwnTemplate`, so its template is a verbatim copy of
`unfuckarr/unraid/unfuckarr.xml`; that file gained the VMAF space-saving prose
and the `UNFUCKARR_RECYCLE_BIN_PATH` / `_DAYS` Config blocks when #3 merged, and
the broken path meant the copy silently fell back to the old committed version.
**Assume any `hasOwnTemplate` app drifted during that window** — regenerating is
the only thing that surfaces it.

`otter-edid-editor` added as a `static-build` (`npm run build` → `dist`,
`public/_headers`), **hostPort 8529**, public, category `MediaApp:Video Tools:`.
19 templates now; the port collision sweep over `templates/*.xml` is clean.
Image built green and is **anonymously pullable** — verified with the
`ghcr.io/token` + manifest GET, not just a green Actions run. Fleet images are
**linux/amd64 only** (checked blend-calc and test-card too), which is what
Unraid wants. See [otter edid editor](https://github.com/stoatworks-labs/otter-edid-editor/blob/main/docs/NOTES.md) (`otter-edid-editor`).

## 2026-08-20 (later) — the generator had been REVERTING Dependabot

Second failure found the moment the generators started working again. The
workflow is a **generated** file, so Dependabot raises action bumps against it
in each app repo, those PRs get merged — and the next `gen-docker.mjs` run puts
the old versions back, silently. Eight repos were already ahead of the
hard-coded pins.

**The fleet was bumped UNEVENLY**, which is what makes this dangerous to "fix"
carelessly: five repos ran `docker/build-push-action@v7` while the rest sat on
v6. Pinning the lower one reverts merged PRs exactly as the hard-coded versions
did. **Pin to the highest major already adopted anywhere in the fleet.**

Versions now live in **`fleet.json` → `actions`** (`checkout`, `setupBuildx`,
`login`, `buildPush`), read by the generator as `fleet.actions`. When a
Dependabot PR bumps one in an app repo, bump it here too. Current: v7 / v4 /
v4 / v7 — all the current majors, so nothing is downgraded. The
`build-push-action` v6→v7 major went through all 16 builds green.

**The check to run before committing any regeneration:**

```bash
git -C <repo> diff -U0 .github/workflows/docker.yml | grep -E '^[+-].*uses:'
```

A removed version *higher* than the added one is a downgrade — stop.

⚠️ **Local checkouts go stale because Dependabot merges on the REMOTE.** Seven
of the eighteen were behind by 1–6 commits, so the first regeneration was built
on stale content and every push was rejected with "fetch first". Recovery:
confirm the only local commit is the generated one and the tree is otherwise
clean, `git reset --hard origin/<branch>`, regenerate, re-commit. **`git fetch`
the whole fleet BEFORE regenerating** or you will do it twice.

**Stage generated files by path, never `git add -A`.** `srt-router` had four
unrelated modified files (a version bump and a `release-lib.sh` change) from
another session; `git add .github/workflows/docker.yml` kept them out and they
are still uncommitted.

`arraycad` is on **`master`**, not `main` — the odd one out in the fleet. The
generated workflow triggers on `[main, master]` so it still builds, but it is
worth normalising.
